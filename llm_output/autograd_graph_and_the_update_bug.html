The autograd graph, and why your training loop breaks at line 2

You asked three things: (1) show me the graph like Karpathy's, (2) why does my code build the wrong graph, and (3) I thought w = w + x and w += x were the same — and what is this no_grad? Answers below, with pictures, and every claim checked against real PyTorch output.

the whole thing in one line

The line weights = weights - (weights.grad * 0.01) peels the name weights off your trainable leaf and sticks it on a brand-new node inside the graph. After that, weights is no longer a leaf, so backward() never fills its .grad — it stays None, and weights.grad.zero_() crashes on the very first pass.

1. Recap: what a graph node even is

In lecture 1 Karpathy drew every Value as a box holding two numbers — its data (the value going forward) and its grad (how much the final loss moves if you nudge this value, filled in going backward). Operations are the little pills between boxes. (Source: karpathy/micrograd.)

adata 3.0grad -2.0   × → cdata -6.0grad 1.0 ← grad flows back
bdata -2.0grad 3.0   (a, b are leaves — you made them directly)

Forward fills data left→right. backward() fills grad right→left. A leaf is a node you created yourself (not the output of an op) — those are the knobs you actually tune.

2. Your bigram net as a graph (one iteration)

Here is exactly what your forward pass builds. Only one node is a leaf — weights, the thing you created with requires_grad=True. Everything else is the output of an operation, so it is a non-leaf. onehot is a plain constant (no grad — it never changes).

onehot weights27×27grad ✓ @→ logits exp→ exp sum→ denom ÷→ probs index→ target_probs log·(-1)→ nulls mean→ loss

The chain of your variables, 1:1 with your code. (exp actually feeds both sum and ÷ — a little branch I straightened out for clarity.)

The one idea that makes the bug obvious: loss.backward() walks this whole chain right→left and computes a gradient for every node — but it only stores the result in .grad for the leaves. The intermediates' grads are computed, used to pass the message further back, and thrown away. So after backward(), exactly one .grad is populated: weights.grad. That is the number your update step reads.

Why only leaves? Because leaves are the only things you ever update. Storing grads for the millions of intermediate nodes would waste memory for numbers you'd never look at.

3. Now the bug: your update rewires the graph

Your update line runs while autograd is still recording. Look at what each piece is:

# weights requires grad, so ANY math on it is recorded as a new graph node
weights = weights - (weights.grad * 0.01)
#         └──────── this subtraction becomes a NEW node (a "SubBackward") ────────┘
# then the name `weights` is re-pointed at that new node.

So the picture changes like this — watch the weights label jump off the blue leaf and land on a red non-leaf:

before the update: weights → leafthe tensorgrad ✓  a real leaf, grad filled
after w = w - lr*g: old leaf −→ new nodeSubBackwardgrad = None ← weights points here now

The label moved. weights is now the output of a subtraction — a non-leaf living inside the graph. Its .grad is None.

Two things break as a result

  • The crash you'll actually see: non-leaf ⇒ backward() won't fill .grad ⇒ weights.grad is None ⇒ None.zero_() throws. This happens on the first loop pass.
  • The quieter disaster (if it didn't crash): your optimizer arithmetic is now part of the graph. Next iteration's backward() would try to differentiate through your own update, and the graph grows every iteration — a memory leak that never frees. An update is you acting on the gradient; it must live outside the math being differentiated.

4. “But w = w + x and w += x are the same!” — not for tensors

Your instinct is correct for numbers, and that's exactly why it misfired here. The rule is about whether the object is mutable:

  • w = w + x  →  always builds a brand-new object, then re-points the name at it. (“rebind”)
  • w += x  →  asks the object to change itself in place (w.__iadd__). If it can (list, tensor, numpy array), the name keeps pointing at the same object. If it can't (int, float, str — immutable), Python quietly falls back to rebinding.

So for an int the two are indistinguishable — nothing to mutate, both make a new int. For a tensor they are genuinely different operations. Verified output:

int — looks the same (immutable)

x = 5; x = x + 1   # new id
x = 5; x += 1      # also new id
# both: id changed? True

list — the tell (mutable)

a=[1,2]; b=a; a += [3]
# a=[1,2,3]  b=[1,2,3]  b saw it!
a=[1,2]; b=a; a = a + [3]
# a=[1,2,3]  b=[1,2]  b did not

The sticky-label picture: the name weights is a label stuck on a jar.

weights → 🫙 jarold + x

weights += x — you top up the same jar. Label never moves. Same object, same leaf, grad intact.

🫙 old → 🫙 newold + x ← weights

weights = weights + x — you fill a new jar and move the label to it. New object; the old jar is left wired into the graph.

5. So what is torch.no_grad()?

torch.no_grad() is a switch that tells autograd “stop recording — don't add anything you see here to the graph.” It's a context manager: everything indented under with torch.no_grad(): runs with recording paused. (docs.)

the picture

backward() works by replaying a tape of every operation the forward pass recorded, in reverse. Your weight update is bookkeeping, not part of the model's math — you don't want it on the tape. no_grad() is the pause button on the tape recorder: do your edit off-tape, then hit record again for the next forward pass. (Same reason you wrap evaluation/inference in it — no tape needed, so it's faster and lighter.)

There's a second reason it's mandatory here. If you try the in-place update without it, PyTorch refuses outright:

# weights -= 0.01 * weights.grad     without no_grad:
RuntimeError: a leaf Variable that requires grad is being used in an in-place operation.

PyTorch blocks it because silently mutating a leaf that's wired into a live graph would corrupt the grads it still needs. no_grad() is you saying “I know — this edit is intentional and off-graph.”

6. The fix, side by side

✗ yours — rebinds onto the graph

loss.backward()
weights = weights - (weights.grad*0.01)
weights.grad.zero_()   # 💥 None

✓ fixed — off-graph, in-place

loss.backward()
with torch.no_grad():
    weights -= 0.01 * weights.grad
weights.grad = None

Two deliberate changes: (1) with torch.no_grad(): so the update isn't recorded, and (2) in-place -= so weights stays the same leaf (keeps requires_grad, keeps getting .grad filled next time). For the reset, weights.grad = None is what Karpathy uses (and what real optimizers do by default); weights.grad.zero_() also works now that weights is a genuine leaf again.

Confirmed it trains. Same loop shape on toy data — buggy version dies on pass 1 with the NoneType error; fixed version's loss falls every step:

buggy loop:  AttributeError 'NoneType' ... 'zero_'
fixed loop:  [1.9923, 1.8126, 1.6447, 1.4889, 1.3454]   # going down = learning
keep this
  • Leaf = a tensor you created with requires_grad=True. Only leaves get .grad filled by backward().
  • w = w + x rebinds (new object); w += x mutates in place (same object). Same for numbers only because numbers can't be mutated.
  • Doing w = w - lr*g turns w into a non-leaf ⇒ w.grad becomes None ⇒ crash, plus the graph leaks.
  • Update rule: always with torch.no_grad(): + in-place, then zero the grad. no_grad = pause the recording tape for off-graph bookkeeping.
